# js-test

컨벤션 확인, 케이스 정리, 작성, 실행 순서로 진행한다. 테스트가 실패하면 원인이 테스트인지 구현인지 구분해서 보고한다.

> 구현 코드는 임의로 고치지 않는다. 구현 버그로 보이면 사용자 확인을 받은 뒤 진행한다.

## 1단계: 대상 확정

- 사용자가 지정한 SUT(테스트할 파일/함수)와 테스트 파일 경로를 확인한다.
- 지정이 없으면 `git diff`와 `git ls-files --others --exclude-standard`로 변경된 파일을 확인하고, 어떤 파일을 대상으로 할지 사용자에게 묻는다.
- 대상이 속한 앱(`service`/`admin`)을 경로로 판별한다. 4단계 실행 명령의 `--filter`에 쓰인다.

## 2단계: 근거 자료 확인

- `docs/test-convention.md`를 읽고 그대로 따른다.
- `docs/glossary.md`를 읽고, 테스트 이름과 변수명에 쓰는 도메인 용어가 일치하는지 확인한다.
- 문서가 다루지 않는 부분은 같은 앱의 기존 테스트 파일을 참고해 스타일을 맞춘다. 문서와 충돌하면 문서가 우선한다.

## 3단계: 테스트 케이스 정리

- SUT를 읽고, 컨벤션에 따라 검증할 케이스 목록을 만든다.
- 이미 있는 테스트 파일이면 먼저 읽고, 같은 동작을 검증하는 테스트가 있는지 확인한다. 중복 케이스는 추가하지 않는다.
- 케이스 목록이 길거나 애매하면, 작성 전에 사용자에게 보여주고 확인받는다.
- 테스트하기 어려운 구조라면 테스트를 억지로 작성하지 않는다. 리팩터링 방법을 사용자에게 제안하고 멈춘다.

## 4단계: 테스트 작성

3단계에서 확정한 케이스를 컨벤션에 맞춰 작성한다. 확정되지 않은 케이스는 추가하지 않는다.
핵심 로직이나 방어 코드를 검증하는 테스트는 구현을 잠깐 바꿔서 실패하는지 확인한다.

## 5단계: 실행 및 확인

작성하거나 수정한 테스트 파일만 실행한다. 경로는 앱 디렉토리 기준이다.

- 예: `pnpm --filter service exec vitest run src/shared/api/apiClient.test.ts`
- 어드민은 `--filter admin`을 쓴다.

**실패 시**

- 실패한 케이스와 에러 메시지를 정리해서 보고한다.
- 원인이 테스트(기대값 오류, 설정 누락 등)인지 구현(실제 버그)인지 구분해서 적는다.
- 테스트 원인이면 수정해서 다시 실행한다. 구현 버그로 보이면 임의로 고치지 않고 사용자에게 확인받는다.

## 완료 후

- 추가·수정한 테스트 케이스와 실행 결과(통과 수)를 요약해서 보고한다.
- 구현 버그나 리팩터링 제안 등 사용자 판단이 필요한 사항이 있으면 함께 정리한다.
