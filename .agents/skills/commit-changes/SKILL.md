# commit-changes

변경사항을 의미 단위로 나누고, 컨벤션에 맞는 메시지로 커밋한다.

## 1단계: 변경사항 확인

- `git status`로 전체 변경 파일을 파악한다. 수정된 파일뿐 아니라 새 파일(untracked)도 여기서 확인한다.
- 내용은 `git diff`(unstaged), `git diff --staged`(staged)로 확인한다. 새 파일은 diff에 나오지 않으므로 파일을 직접 읽는다.
- 의도치 않게 포함된 파일이 있는지 확인한다. (`.env`, 임시 파일, 디버그용 로그 등)
- 발견되면 커밋에서 제외하고 사용자에게 알린다.

## 2단계: 커밋 단위 분리

- 하나의 커밋 = 하나의 목적을 기준으로 나눈다.
- 예: "API 연동"과 "UI 스타일링"이 섞여 있으면 커밋 2개로 분리한다.
- 단위를 나누기 애매하면 사용자에게 확인받는다.

## 3단계: 커밋 메시지 작성

`docs/commit-convention.md`를 읽고 커밋 컨벤션을 따른다.

## 4단계: 커밋 및 훅 처리

커밋 시 husky 훅이 실행된다.

- `pre-commit`: lint-staged (staged 파일에 prettier + eslint --fix)
- `commit-msg`: commitlint (커밋 메시지 형식 검사)

**규칙**

- `--no-verify`로 훅을 건너뛰지 않는다.
- 훅 실패 시 커밋은 만들어지지 않는다. `--amend`로 이전 커밋을 수정하지 말고, 원인을 고친 뒤 새로 커밋한다.

**실패 유형별 대응**

- **commitlint 실패**: 에러 메시지(type, 형식 등)에 맞게 메시지를 고쳐 다시 커밋한다.
- **eslint 실패 (자동 수정 불가)**: 에러를 정리해 사용자에게 보고하고, 수정 방향을 제안하되 임의로 코드를 고치지 않고 확인을 받는다.
- **훅이 파일을 수정한 경우** (prettier/eslint --fix): 커밋 후 `git status`를 확인해 훅이 고친 변경이 남아있으면 사용자에게 알린다. (lint-staged는 보통 수정분을 커밋에 자동 포함하지만, 부분 staging 등으로 남는 경우가 있다)

## 완료 후

- 생성된 커밋 목록(해시, 메시지)을 요약해서 보고한다.
- push는 사용자 확인 후 진행한다. (자동으로 push하지 않음)
